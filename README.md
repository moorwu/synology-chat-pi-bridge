# Synology Chat Pi Bridge

[中文文档](README.zh-CN.md)

A self-hosted bridge between Synology Chat webhooks and a local `pi` agent. It lets Synology Chat channels talk to an agent running on your LAN, with channel sessions, replies, file attachments, and generated media previews.

## Features

- Receives Synology Chat outgoing webhooks.
- Replies through Synology Chat incoming webhooks.
- Supports multiple outgoing tokens.
- Supports per-channel incoming webhook mapping, by channel name or channel ID.
- Keeps separate Pi sessions by channel/user.
- Supports text commands: `/status`, `/new`, `/abort`, `/compact`, `/model`, `/trace`.
- Downloads user-sent attachment URLs when Synology includes them in the outgoing payload.
- Publishes local files generated by the agent through an internal `/files/...` endpoint and sends them back via Synology `file_url`.
- Runs fully on your LAN.

## Requirements

- [Bun](https://bun.sh/)
- A working `pi` CLI with JSON-RPC support
- Synology Chat installed and reachable from the bridge host
- The NAS must be able to fetch `SYNOLOGY_CHAT_FILE_BASE_URL`

## Quick Start

```bash
git clone https://github.com/YOUR_NAME/synology-chat-pi-bridge.git
cd synology-chat-pi-bridge
bun install
cp .env.example ~/.config/synology-chat-pi-bridge.env
vim ~/.config/synology-chat-pi-bridge.env
bun run synology
```

Open `http://BRIDGE_HOST:8789/health`; it should return `OK`.

## Synology Chat Setup

In Synology Chat, open **Integration**.

### Incoming webhook

Create an incoming webhook for the channel where the bot should reply.

Copy the webhook URL to:

```env
SYNOLOGY_CHAT_INCOMING_URL=...
```

For multi-channel replies, create one incoming webhook per channel and configure:

```env
SYNOLOGY_CHAT_INCOMING_URLS_JSON={"general":"...","1":"...","random":"...","2":"..."}
```

Synology sometimes sends a channel name and sometimes only a channel ID. If in doubt, map both.

### Outgoing webhook

Create an outgoing webhook:

- Channel: either a specific channel or any public channel
- Trigger word: for mention-style use, set something like `@pi`
- URL: `http://BRIDGE_HOST:8789/synology-chat/webhook`
- Token: copy to `SYNOLOGY_CHAT_OUTGOING_TOKEN`

For a dedicated channel where every message should trigger the bot, create an outgoing webhook for that channel with an empty trigger word. Add the bot's incoming webhook display name to `SYNOLOGY_CHAT_IGNORE_USERS` to prevent self-trigger loops.

## Attachments and Generated Files

Synology incoming webhooks support `file_url`. This bridge exposes generated files under:

```text
http://BRIDGE_HOST:8789/files/<file>
```

Set:

```env
SYNOLOGY_CHAT_FILE_BASE_URL=http://BRIDGE_HOST:8789
```

When the agent replies with a local path such as:

```text
/home/user/project/output/image.png
```

the bridge copies the file into its public directory and sends it back to Synology Chat as a file attachment.

The bridge recognizes common image, video, audio, archive, text, PDF, JSON, and CSV file extensions.

## Commands

Send these from Synology Chat:

```text
/status
/new
/abort
/compact optional reason
/model local
/trace on
/trace off
/trace status
traceon
traceoff
```

`/trace on` or `traceon` streams compact `TRACE start/end` messages for tool calls, then appends a diagnostic summary after each agent turn. It also shows any `SKILL.md` files read during the turn, which is the bridge's best signal for skill usage.

The `/model` command is optional. Configure targets with:

```env
PI_MODEL_TARGETS_JSON={"local":{"provider":"example-provider","model":"example-model","label":"Local model"}}
PI_MODEL_ALIASES_JSON={"fast":"local","local":"local"}
```

## systemd User Service

```bash
mkdir -p ~/.config/systemd/user
cp systemd-user.service.example ~/.config/systemd/user/synology-chat-pi-bridge.service
systemctl --user daemon-reload
systemctl --user enable --now synology-chat-pi-bridge.service
journalctl --user -u synology-chat-pi-bridge.service -f
```

## Security Notes

- Do not expose this bridge directly to the public internet.
- Keep Synology webhook tokens secret.
- Use firewall rules or a reverse proxy allowlist if the bridge is reachable outside your LAN.
- `/files/...` serves files copied into the bridge public directory. Treat it as LAN-visible.
- Use a cleanup job for old files in `PI_SYNOLOGY_DATA_DIR/public` and `uploads` if you generate many files.

## Status

Alpha. The bridge is usable, but Synology outgoing attachment payloads vary by version and client. Raw payloads are logged to `payloads.jsonl` for debugging.
